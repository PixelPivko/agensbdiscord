# Агент Службы Безопасности — ТОРТИК PROJECT

Самостоятельный Discord-бот на Python 3.12 + discord.py 2.x. Не связан с SCP:SL / TortikReborn.
Верификация, модерация, антимат, предупреждения, XP и автоматические роли.

Проект поставляется **без токена и без соединения с вашим Discord-сервером**.
Все указанные в ТЗ роли уже внесены. Нужно заполнить ID сервера, канала проверки и modlog.
Шаблон с нулевыми ID проходит офлайн-проверку структуры, но блокирует сетевой запуск.

## Настройки Discord перед запуском

1. Создайте приложение и Bot в [Discord Developer Portal](https://discord.com/developers/applications).
   Название: **Агент Службы Безопасности**. Включите Server Members Intent и Message Content Intent.
   Presence intent и голосовые возможности не нужны. Если Discord требует одобрения привилегированных intents
   для вашего приложения, оформите его до запуска.
2. Установите приложение в сервер со scopes `bot` и `applications.commands`.
3. Выдайте боту: **Manage Roles, Manage Messages, Moderate Members, Kick Members, Ban Members,
   View Channels, Send Messages, Embed Links, Read Message History**. Administrator не требуется.
   Проверьте также переопределения прав в каждом модерируемом канале и ветках.
4. Поднимите роль бота выше всех автоматически выдаваемых ролей и участников, которых он должен модерировать.
   Роли с Administrator или Manage Roles запрещены для автоматической выдачи.
5. В `config/config.yml` замените ключ `guilds: 0:` на числовой ID сервера.
   Задайте ненулевые `verification_channel_id` и `modlog_channel_id`.
   Не меняйте существующие role IDs, если они соответствуют вашему серверу.
6. Сделайте канал modlog закрытым для обычных участников: журнал содержит причины модерации и ID.
   Канал проверки должен быть виден новичкам. Боту нужны отправка сообщений, embeds и история сообщений.
7. Настройте права `@everyone` так, чтобы непроверенные участники не могли писать/вступать в голосовые каналы
   после естественного истечения timeout или во время остановки бота. Доступ к обычным каналам должен даваться
   проверенными стартовыми ролями. Проверьте все остальные роли и channel overrides: разрешение другой роли
   может открыть доступ. Бот не переписывает права сервера автоматически.
8. В Server Settings → Integrations убедитесь, что настроенная staff-role может запускать команды приложения.
   Команды проверяют staff-role/Administrator/owner внутри бота, а не только видимость команд в клиенте.

Для дополнительного сервера добавьте отдельный блок под `guilds` с его собственными IDs и настройками.
Не копируйте ID ролей первого сервера во второй. Ненастроенные серверы игнорируются.
Команды регистрируются отдельно только в настроенных серверах.

## Верификация и captcha

Новый участник → SQLite `pending` → timeout на 7 дней → DM с embed и кнопкой → modal с примером.
Операнды 1–10, сложение/вычитание/умножение, целый неотрицательный ответ. Параметры по умолчанию:
600 секунд, 5 попыток, повторная отправка не чаще одного раза в 60 секунд.

Каждая captcha хранит `(guild_id, user_id)`, nonce, вопрос, ожидаемый ответ, время создания и число попыток.
Ожидаемый ответ хранится в SQLite, не выводится в лог и не отправляется в Discord. Доступ к БД ограничьте
системным пользователем сервиса. Кнопка не содержит ответ или ID проверяемого пользователя: она открывает
проверку именно для нажавшего участника, только в соответствующем сервере. У modal есть проверка владельца
и nonce. После 5 ошибок нужно дождаться истечения текущего окна, затем кнопка создаст новый пример.
Ошибка в captcha не создаёт warn и не приводит к бану.

Кнопки имеют постоянные `custom_id` и `timeout=None`, повторно регистрируются при старте.
Старое сообщение с кнопкой продолжает работать после перезапуска. Уже открытый modal после перезапуска
может устареть: нажмите кнопку ещё раз; состояние попыток останется в SQLite.

После правильного ответа сохраняется `passed`, **сразу снимается timeout проверки**, затем сохраняется
`verified` и выдаются семь join roles + одна пара ролей уровня. Раннее сохранение `verified` после снятия timeout
позволяет восстановить недовыданные роли после сбоя. Если Discord временно не позволяет снять timeout,
остаётся `passed`, завершение повторяет фоновое восстановление. Ошибка одной роли фиксируется и не отменяет
успешную captcha. Отдельный timeout модерации сохраняется; captcha не служит способом отменить наказание.

Параметр `give_join_roles_before_verification` оставлен в config со значением `false`.
Эта сборка отклоняет `true`, чтобы сохранить требование выдачи ролей только после проверки.

Проверенный участник при повторном входе не проходит captcha заново. `/verification reset` возвращает
`pending`, удаляет управляемые стартовые/уровневые роли, снова ставит timeout и отправляет captcha.
Если Discord не разрешит timeout/удаление роли, ошибка попадёт в журнал; ограничения доступа через
настроенные channel permissions остаются обязательной частью настройки сервера.

### Закрытые DM: ограничение платформы

Discord timeout ограничивает взаимодействие пользователя в сервере, поэтому публичная кнопка не является
надёжным способом обойти действующий timeout. При ошибке DM бот публикует в канале проверки инструкцию:
включить личные сообщения от участников сервера и попросить сотрудника выполнить `/verification resend`.
Панель `/verification panel` предоставляет постоянную кнопку для участника, которому доступно взаимодействие.
**Бот не снимает timeout ради fallback.** Если пользователь не может обратиться к staff внутри сервера,
заранее разместите доступный внешний контакт поддержки в описании канала проверки.

На первом запуске ранее существовавшие участники не подвергаются массовому timeout.
Для включения такого участника в проверку используйте `/verification reset`. Пока `verified` отсутствует,
автоматический XP ему не начисляется. После первой успешной работы бот хранит время сверки и восстанавливает
обработку пропущенных вступлений при следующем запуске. Ушедшие участники сохраняются в базе для rejoin.

## Slash commands

| Команда | Доступ / назначение |
| --- | --- |
| `/level [user]` | Все: уровень, XP внутри уровня и до следующего |
| `/leaderboard` | Все: топ-10 проверенных участников без пингов |
| `/verification reset user` | Staff: повторная обязательная проверка |
| `/verification resend user` | Staff: повторить DM для pending |
| `/verification panel` | Staff: постоянная панель в настроенном канале |
| `/warn user reason` | Staff: предупреждение и возможная escalation |
| `/warnings user` | Staff: последние 20 активных предупреждений |
| `/unwarn warning_id` | Staff: снять конкретное предупреждение текущего сервера |
| `/clearwarns user` | Staff: снять все предупреждения участника |
| `/timeout user minutes reason` | Staff: от 1 до 40320 минут |
| `/untimeout user reason` | Staff: снять наказание, сохранив ограничение проверки |
| `/kick user reason` | Staff: исключить участника |
| `/ban user reason` | Staff: бан, без удаления истории |
| `/unban user_id reason` | Staff: снять бан по строковому Discord ID |
| `/purge amount` | Staff: удалить 1–100 сообщений текущего канала |
| `/userinfo user` | Staff: техническая информация об участнике |
| `/modlog [user]` | Staff: последние 15 событий из SQLite |
| `/xp add user amount` | Staff: добавить XP |
| `/xp remove user amount` | Staff: убрать XP с нижней границей 0 |
| `/xp set user amount` | Staff: установить XP |
| `/levels set user level` | Staff: установить уровень 0–1000 |
| `/levels sync user` | Staff: исправить управляемые роли одного участника |
| `/levels syncall` | Только Administrator/owner: фоновая сверка всех записанных участников |

`/level` оставлен отдельной командой просмотра. Discord не позволяет одновременно иметь одноимённую
команду с параметром пользователя и группу подкоманд `/level set`; поэтому изменение — **`/levels set`**.

Staff — роль `1546592219379666996`, Administrator или владелец сервера. Для действий над участником
проверяется иерархия сотрудника и бота. Нельзя модерировать владельца, себя, самого бота, равного или
вышестоящего участника. Owner обходит только ограничение собственной роли, но не иерархию бота и правила Discord.
Даже Administrator подчиняется иерархии в этом приложении. Для ручной синхронизации и изменения XP выдаваемые
роли должны быть ниже сотрудника, кроме owner. Discord не разрешает timeout администраторов.

## Антимат и предупреждения

`config/profanity.json` содержит начальный список точных запрещённых слов; формы слов добавляются явно.
`config/whitelist.json` имеет приоритет. Нормализация: NFKC, нижний регистр, ё→е, пробелы;
поддержаны очевидные разделители между буквами. Проверяются границы слова, а не короткие подстроки.
Транслитерация и все возможные способы обхода фильтра не распознаются. Настройте словарь под правила сообщества.

Проверяются новые сообщения и изменения сообщений. При нарушении бот удаляет сообщение, сохраняет warn,
отправляет короткое DM-уведомление и modlog. Текст удалённого сообщения и содержимое приватных DM не логируются.
Повторное событие для одного message ID не создаёт второй warn. Если удаление запрещено Discord, ошибка
логируется, предупреждение всё равно сохраняется, XP не начисляется. Боты исключены.
Исключения — `ignored_channels`, `ignored_roles`, опциональный `staff_immune` (по умолчанию `false`).

Пороги `moderation.warn_actions` срабатывают при достижении точного числа активных предупреждений:
3 → 10 минут; 5 → 60 минут; 7 → 1440 минут; 10 → запись `staff_attention` в modlog.
Автобан **выключен**; его можно явно включить `ban: true` на нужном пороге.
Иерархия и права проверяются до автоматического наказания. Снять warn не означает автоматически снять timeout.
Ошибки escalation фиксируются; опасное наказание после неопределённого сетевого результата автоматически
не повторяется — staff проверяет `/modlog`.

## XP и роли

Начальные параметры: 1–3 XP максимум раз в 60 секунд, минимальная длина сообщения 5 символов.
Боты, команды с префиксами `/`, `!`, `?`, исключённые каналы/роли и непроверенные пользователи не получают XP.
Хэши повторяющихся сообщений хранятся час; cooldown и история переживают перезапуск. Более 5 подходящих
сообщений за 10 секунд блокируют дополнительные начисления. Cooldown проверяется в транзакции SQLite,
поэтому одновременные события не дают несколько наград.

Начисление происходит через 3 секунды, после проверки существования и неизменности сообщения.
Удалённые до этой проверки сообщения и нарушения собственного фильтра не получают XP. Событие удаления
после начисления отменяет награду, в том числе при массовом удалении. Квитанции хранятся 30 дней.
Если удаление произошло во время полного отключения бота или после срока хранения, надёжно отменить
старую награду без истории Discord невозможно. Native AutoMod заблокированное сообщение не создаёт обычное
событие сообщения. Уже выданные XP не растут от редактирования.

Суммарный XP для уровня `L`: **50 × L × (L + 1)**. Переход с `L` на `L+1` стоит `100 × (L+1)` XP.
Предел: уровень 1000, 50 050 000 XP. Уровень вычисляется из XP без отдельного рассинхронизируемого поля.

| Уровни | Первая роль | Вторая роль |
| --- | --- | --- |
| 0–4 | 1546592219220152347 | 1546592219274940458 |
| 5–9 | 1546592219220152348 | 1546592219274940460 |
| 10–14 | 1546592219220152346 | 1546592219274940459 |
| 15–19 | 1546592219220152349 | 1546592219274940461 |
| 20–1000 | 1546592219274940456 | 1546592219274940462 |

Сначала снимается старая пара, затем выдаётся новая. Другие роли не переписываются. Если старую пару
удалить нельзя, новая не добавляется. Временное неполное состояние из-за сбоя Discord исправляется сверкой
на старте и каждые 900 секунд, а также `/levels sync`. Сверка последовательная, с паузой 0,5 секунды на
участника, плюс штатная обработка HTTP rate limits в discord.py. Результат пишется в modlog.

## SQLite, логи и эксплуатация

База по умолчанию: `data/security_agent.db`. WAL + busy timeout 5 секунд, параметризованные SQL-запросы,
сериализованные транзакции. Таблицы: `users`, `verification`, `captcha_sessions`, `warnings`, `xp`,
`xp_events`, `deleted_messages`, `moderation_actions`, `guild_state`, `schema_version`. В запросах пользовательских данных
всегда присутствует `guild_id`; ID предупреждения не даёт доступ к другому серверу.

Журнал JSON идёт в stdout/journald. Modlog дополнительно хранится в SQLite с очередью доставки в Discord;
при временном отсутствии канала события останутся в базе. Возможна повторная доставка события после
сбоя между отправкой и сохранением отметки доставки; у каждого события есть ID.
Обычные ответы команд приватные, mentions по умолчанию выключены. Единственный намеренный пинг новичка —
инструкция fallback в канале проверки. Staff attention записывается без массовых пингов.

Запускайте **один процесс** на одну SQLite-базу. Уровень конкуренции рассчитан на один async-процесс;
несколько независимых копий бота могут повторять Discord-действия. Для резервного копирования остановите
сервис и копируйте всю папку `data`, затем возобновите работу. Не копируйте только основной файл активной
WAL-базы. Токен хранится только в `.env`; не прикладывайте `.env` и рабочую БД к сообщениям/репозиторию.

## Ubuntu 24.04: точный порядок установки

Команды ниже предназначены **для вашего Ubuntu-сервера**. Они не выполнялись автоматически при сборке.
Распакуйте `security-agent.zip` в домашнюю папку, чтобы появился `~/security-agent/`.

```bash
sudo apt update
sudo apt install -y python3.12 python3.12-venv unzip
sudo useradd --system --user-group --home-dir /opt/security-agent --shell /usr/sbin/nologin security-agent
sudo install -d -o security-agent -g security-agent -m 0750 /opt/security-agent
sudo cp -a ~/security-agent/. /opt/security-agent/
sudo chown -R security-agent:security-agent /opt/security-agent
cd /opt/security-agent
sudo -u security-agent python3.12 -m venv .venv
sudo -u security-agent .venv/bin/python -m pip install -r requirements-dev.lock
sudo -u security-agent .venv/bin/python -m pytest -q
sudo -u security-agent .venv/bin/python -m ruff check .
sudo -u security-agent .venv/bin/python bot.py --check
```

Если системный пользователь или каталог уже создан, пропустите его создание; не удаляйте существующие данные.
Для окружения без тестовых инструментов вместо `requirements-dev.lock` используется `requirements.lock`.

Заполните настройки и токен в редакторе, без вставки токена в командную строку:

```bash
sudo -u security-agent cp .env.example .env
sudo chmod 600 .env
sudo nano /opt/security-agent/.env
sudo nano /opt/security-agent/config/config.yml
sudo -u security-agent .venv/bin/python bot.py --check
```

В `.env` должна быть строка `DISCORD_TOKEN=ваш_токен`. Никому её не отправляйте.
В config задайте реальные ID сервера и каналов, настройте Discord permissions по инструкции выше.
Следующая команда **соединяется с Discord с вашим токеном**, но только проверяет сервер, роли и права;
не синхронизирует команды, не назначает роли/timeout, не отправляет сообщения:

```bash
sudo -u security-agent .venv/bin/python bot.py --preflight
```

Успех — все права/каналы/роли OK и код завершения 0. При ошибках код 2.
Офлайн `--check` не может проверить существование реальных ролей или channel overrides.
`--preflight` проверяет права бота в каналах проверки и modlog, но не доказывает правильность всей модели
доступа участников к каждому каналу сервера. Проверьте её отдельным тестовым аккаунтом.

После успешной проверки и готовности к обработке событий выполните обычный запуск:

```bash
sudo -u security-agent .venv/bin/python bot.py
```

Обычный запуск регистрирует команды, восстанавливает незавершённые проверки, исправляет управляемые роли
и начинает обрабатывать сообщения. Для первого функционального прогона используйте отдельный тестовый
Discord-сервер и замените все role/channel IDs в его блоке config. Остановите ручной процесс Ctrl+C
перед включением systemd, чтобы не было двух экземпляров.

### Systemd

Готовый unit: `deploy/security-agent.service`. Токен берётся из `/opt/security-agent/.env`.
Пользователь без shell, строгие права файлов, запись разрешена только в `data`, SIGTERM завершает соединения.

```bash
sudo install -m 0644 deploy/security-agent.service /etc/systemd/system/security-agent.service
sudo systemctl daemon-reload
sudo systemctl enable --now security-agent.service
sudo systemctl status security-agent.service --no-pager
sudo journalctl -u security-agent.service -n 100 --no-pager
```

Изменение config/словаря применяется после `sudo systemctl restart security-agent.service`.
Остановка: `sudo systemctl stop security-agent.service`. Unit перезапускает процесс только при ошибке,
ограничивая число неудачных запусков. Не включайте DEBUG для сетевых библиотек.

## Проверки и ограничения

Сводка фактически выполненных локальных проверок — `REPORT.md`.
Тесты используют настоящую временную SQLite и mock Discord API; они не доказывают реальную доступность
конкретных ролей, channels, intents и взаимодействий в клиенте Discord. Проверка на Ubuntu и живом тестовом
сервере остаётся этапом развёртывания пользователя. Голосовые зависимости не нужны; соответствующие
предупреждения discord.py при офлайн-проверке ожидаемы.

В коде нет eval, Discord shell-команд, выполнения пользовательского Python, чтения `.env` через Discord,
экспорта БД для пользователей, скрытого owner ID или административного backdoor.

Справка платформы: [timeout и permissions](https://github.com/discord/discord-api-docs/blob/main/developers/topics/permissions.mdx),
[slash commands](https://docs.discord.com/developers/docs/interactions/slash-commands),
[discord.py interactions и persistent views](https://discordpy.readthedocs.io/en/stable/interactions/api.html).
